## Context

参见 [proposal.md](proposal.md)。项目目前只有单场测试模式和空的正式比赛入口；`players.csv` 为每名球员保存七项基础属性和正式版静态词条，`resources/data/` 尚无完整球队、阵容和词条表，也没有筹码、赔率、注单或跨场存档。拆分后，add-formal-match-foundation 提供球队/阵容和只读比赛结果，add-player-ai 提供整场自主比赛，add-player-traits 提供词条定义、效果和覆盖接口；complete-ai-match-demo 只提供前置动作规则。

项目要求可表格化静态数据用 CSV，规则层不依赖场景节点且随机源可复现。下注、赔率、挑战进度需要在场景以外以强类型数据和独立服务实现。新增模块编码前须补齐 Notion《设计文档》下的专题策划页和《程序架构》下的程序设计子页；全局《程序架构》《模块接口》用于核对边界。默认不做截图、录屏或离屏渲染测试。

## Goals / Non-Goals

**Goals:**

- 一个总种子足以重建 Demo 词条组合；每场比赛与每次重试使用与下注操作无关的派生种子。
- 赔率、注单与筹码可在无比赛场景环境中分别测试，跨场存档和中途取消保持原子性。
- 赛事只有一个正式结果来源；下注系统只读取比赛快照与事件。

**Non-Goals:**

- 真实货币、账户服务、支付、联网赔率、社交排行。
- 把 Demo 随机词条写回 `players.csv`，或改变正式版本的 CSV 词条配置。
- 按词条、当前体力、击倒等临时状态重新计算赔率；Demo 仅售全场胜／平／负，不做部分卖出或下一球市场。

## Decisions

### 1. 挑战与比赛之间采用只读快照接口

挑战服务持有固定队伍、五位按配置排列的不同对手、总种子、当前场次、重试次数、生成词条和筹码检查点。比赛服务仅接收选定阵容、Demo 词条覆盖和派生比赛种子；下注服务只读已完成固定步的比分、阶段、剩余时间与正式赛果。下注/卖出不写比赛状态，也不调用比赛随机源。

备选是在 `MatchSimulation` 中加入赔率和余额字段；这会破坏确定性规则层的职责，且难以单测或处理退出回滚，因此不采用。域服务可以使用测试快照注入，在正式比赛尚未完成时先实现下注逻辑；接口集成等待 add-formal-match-foundation，最终观赛体验等待 add-player-ai 和 add-player-traits。

### 2. 总种子进行域隔离的稳定派生

挑战开始时生成或接收总种子，作为本轮记录的一部分展示。使用固定、跨平台稳定的派生算法和域标签：`trait(master_seed, player_id)` 决定各球员词条；`match(master_seed, match_index, retry_count)` 决定比赛种子。这样增删下注调用、改变球员遍历顺序或重试比赛都不会重排既有球员词条。生成的 3–5 个 trait IDs 每人不重复，只从 `traits.csv` 中符合位置条件的稳定 ID 集合选择，存入挑战快照；正式模式仍采用 `players.csv` 的 trait IDs。备选是共用一个依次抽数的全局随机流，会被 UI 和加载顺序意外影响，因此不采用。

### 3. 静态数据与本地进度分层

`players.csv` 继续提供基础属性与正式版词条。teams.csv 与 team_players.csv 的定义/加载/阵容校验归正式比赛基础；traits.csv 的定义/加载/分配校验归词条特性。本 change 复用这些仓库，只增加挑战配置、五场固定对阵表及挑战特有的对手/候选引用校验。总种子派生、Demo 随机词条生成与跨五场保存仍由挑战拥有，不迁入词条效果特性。初始筹码、最低下注额、赔率模型参数、显示精度由表格配置。

本地存档只保存运行时数据：存档版本、静态数据版本标识、总种子、生成词条、已完成场次、余额、当前场赛前检查点和重试次数。使用临时文件加原子替换保存；读取损坏或与当前数据版本不兼容时给出明确错误，不静默篡改余额。新挑战由明确操作重置到配置的初始筹码。备选是把本场每帧状态和未结算注单作为可恢复赛况存档，会要求完整比赛恢复，与已确认的中途取消规则冲突，因此不采用。

### 4. 一场比赛是独立的筹码交易单元

进入某场赛前时记录唯一检查点余额；本场下注扣款、卖出返还和终场派彩在独立账本上发生。收到唯一正式终场结果后，先幂等结算全部未卖出注单，再原子提交新余额和下一场进度。中途退出或启动时发现未终场的场次，恢复检查点余额并作废该场全部下注/卖出，重试次数加一；已完成场次不回滚。这样即使已卖出获利，也不能靠退出反复刷筹码。

每笔注单有稳定 ID、比赛 ID、所押结果、下注额、接受赔率、状态和账本事件。所有筹码采用固定精度的最小单位存储，返还金额在入账边界按统一规则舍入；显示赔率与接受报价采用一致精度，舍入误差单独测试，不设置隐藏抽水。余额不足、金额无效、重复卖出、重复结算与过期报价均返回明确失败且无副作用。

### 5. 公平赔率来自剩余进球分布

按上场位置对七项基础属性给不同权重，形成双方进攻与防守能力；门将的守门值主要进入防守，前场射门/技巧主要进入进攻。可配置参数把双方攻防对比转为全场预期进球。赛中按剩余时间比例得到双方剩余预期进球，在当前比分上枚举双方未来进球分布并汇总终场主胜/平/客胜概率，再归一化。只在市场开放且结果未确定时发布正概率、十进制公平赔率 `1 / probability`；赔率不含抽水。概率计算为纯函数，不抽随机数。固定测试报价只通过测试注入接口提供。

备选是对比分和时间直接写手工赔率表；它难以让双方实力与平局概率一致，也不易扩展到不同对手，因此不采用。具体权重、预期进球标尺和计算截断精度均为可配置调参值，验收关注概率归一、输入隔离、单调趋势与确定性。

### 6. 交易使用比赛步号与报价版本

市场在赛前准备与正常比赛回合开放；进球确认、球网运动、重置、暂停结算与终场关闭。每次比分或时间报价更新生成新的版本，界面提交下注/卖出时带上所见版本；服务在同一个已完成比赛步的快照上复核状态、赔率、余额和注单状态，过期则拒绝并返回新报价供确认。不会静默改价。

卖出仅适用于未卖出的本场注单，返还额为 `stake × accepted_decimal_odds × current_probability_of_selected_outcome`，无额外折价。下注接受赔率锁定，随后赔率变化不改变潜在终场返还。终场按官方赛果对未卖出注单派彩一次；已卖出注单不再结算。概率与筹码精度规则保持一致，避免零下注、负余额或重复入账。

## Risks / Trade-offs

- **显示赔率四舍五入可能造成微小套利或“无抽水”观感偏差** → 内部使用明确精度，锁定实际可成交报价，并对入账舍入和即时卖出案例设测试；不添加隐性折价。
- **总种子可手动复用，结果可能被玩家事先知道** → 这是 Demo 的复现能力，不做竞争排行榜；后续若引入排行需另定防重放规则。
- **现有球员表词条为静态列，与 Demo 随机词条看似冲突** → 使用只读本轮覆盖，不改 CSV；文档明确 Demo 与正式版分支。
- **本地存档中断可能造成余额/场次不一致** → 使用单一检查点与原子保存，重复终场结果幂等，启动时把未终场比赛整体回滚。
- **比赛结果模型和真实 AI 比赛分布不完全吻合** → 将权重及预期进球率配置化，用固定种子批量比赛统计校准；不改变无抽水的换算方式。

## Migration Plan

先按项目要求建立 Notion 挑战/下注专题策划页及《程序架构》下的程序设计子页，补齐静态数据表及校验器；随后以测试比赛快照实现挑战、定价和注单服务。待 `add-formal-match-foundation` 的只读比赛契约就绪，再接入真实比赛和赛前/赛中 UI；全 AI 五场验收同时等待 `add-player-ai` 与 `add-player-traits`。正式版球员 CSV 保持原样；若新功能回退，可不加载挑战入口，原独立测试模式继续可用。
